# 11 安全、个人信息与平台合规需求

## 前提
跨平台订单处理涉及消费者手机号、收货地址、姓名、面单密文、商家OAuth凭据、采购资金行为。商家授权读取店铺订单不意味着许可把消费者收件数据交给任意第三方买家账号。

## 安全威胁与控制
| 威胁 | 控制 |
|---|---|
| 跨租户横向越权/BOLA | 每个读写端点从会话确认租户，校验对象tenant和店铺范围；E2E安全测试 |
| token泄漏 | KMS/Secret Manager中保存凭据；最小scope；禁止写日志；轮换与撤销 |
| 回调伪造 | 官方签名、时间窗、重放nonce/eventId、必要时状态回查 |
| SQL注入/XSS/CSRF | 参数化SQL、输出编码、CSP、SameSite/CSRF保护 |
| SSRF | 外部URL白名单、DNS/IP校验，禁止接入内网元数据地址 |
| 支付双扣/伪造成功 | 唯一请求、UNKNOWN冻结、官方权威校验 |
| 订单隐私滥用 | 不存明文地址，平台认可密文/面单通道，敏感数据只在受控环境最小处理 |
| 运营人员滥权 | 角色最小化、双人审批、审计日志、支持人员临时授权 |
| 文件导出泄露 | 细粒度权限、脱敏、水印、短有效期、下载审计 |
| 依赖/供应链攻击 | 锁定依赖、SCA、镜像扫描、SBOM、签名部署 |

## 数据分级
- P0高度敏感：支付签约凭证、服务端应用密钥、OAuth access/refresh token、解密密钥。
- P1敏感：消费者PII与面单密文、客服工单、订单原始详情。
- P2业务机密：采购价格、供应商ID、销售金额、利润。
- P3公开或低敏：自研UI资源、帮助文档。
不可以在普通API日志/消息队列记录P0/P1明文；密文同样按敏感数据控制传播。

## 最小化数据流
- 接收来源平台签名事件，仅持久化必要ID和状态。
- 需要采购履约时通过合法平台认可的密文能力将必要字段交给1688供应商，不在通用业务库落地解密地址。
- 无可行密文履约途径：阻止自动采购并明确告知商家，而不是强迫商家解密复制信息。
- 回调、监控、审计中的邮箱/手机号、商家标识采用脱敏/散列。

## 用户权利与合规运营
- 编制《用户协议》《隐私政策》《商家数据处理协议》《第三方信息共享说明》《服务退出与数据删除方案》，正式上线前经专业律师核查。
- 建立商家数据控制者/受托处理者角色界定与再委托处理清单；处理范围按各平台协议收紧。
- 保留合同和财务依法要求记录，但对超期个人数据清理；响应数据查询/删除/撤回委托等请求。
- 如果确需跨境处理数据、特殊行业处理或大规模个人信息活动，单独评估额外法律义务；本期默认中国大陆合规区域部署。
- 供应商层面使用加密传输、最小访问权限与保密/数据处理约定。

## 外部标准及核查入口
- 中国《个人信息保护法》及网络安全、数据安全适用要求；以正式法律及法务意见为准。
- 抖店开放平台安全规范、商品供应链类目、抖店云及密文政策：`https://op.jinritemai.com/docs`。
- 淘宝开放平台订单隐私与1688密文分销：`https://developer.alibaba.com/docs/doc.htm?articleId=122128&docType=1&treeId=1`。

## 上线安全检查
- [ ] 100%业务API具备授权检查及跨租户反向测试。
- [ ] P0密钥不出Secret Manager，正式环境没有明文配置。
- [ ] 仅启用通过平台审批的能力，支持紧急停用。
- [ ] 敏感操作MFA/双人审批、异常警报、日志脱敏。
- [ ] 处理路径的数据图谱、留存期限、第三方共享与删除方案已经法务签字。
- [ ] 基础渗透测试及修复，包含回调伪造、IDOR、支付重复提交和导出隐私。
