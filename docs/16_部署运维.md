# 16 环境、部署、备份、监控与故障预案

## 环境
- local：Docker Compose + Mock通道 + 演示租户和合成订单；默认禁止真实外部API。
- staging：近生产数据库结构、脱敏/合成数据、官方sandbox账号（如获批）；禁止调用生产扣款。
- production：分区网络、KMS、加密数据库、独立备份、WAF和监控；生产Feature Flag初始全关闭。

## 环境配置范例
见根目录 `.env.example`。严禁把生产KMS凭据、支付秘钥、OAuth token或客户信息提交Git。开发种子账号不得存在于生产部署。

## 容器与组件
- web Nginx静态文件及API反向代理；api Spring Boot；worker Spring Boot worker-profile；PostgreSQL；Redis；RabbitMQ；OTel/metrics。
- 开发启动脚本应先检测数据库与队列健康；生产接入参数通过Secret Manager注入，且日志屏蔽敏感变量。
- 使用Flyway自动执行已审核迁移，必须支持备份/演练/回滚方案，不能靠DDL自动更新。

## 灰度上线
1. 开发Mock端到端验收。
2. 平台审批证明和官方Sandbox测试。
3. 仅指定真实商家白名单 + `MANUAL` 模式上线。
4. 确认对账/隐私/异常单处理无重大问题后，允许少数签约商家 AUTO 小额交易。
5. 持续观察支付UNKNOWN、重复创单、物流回填，指标稳定后扩大。

## 监控告警
| 告警 | 建议分级 | 响应 |
|---|---|---|
| payment_unknown_count > 0持续增长 | P1 | 暂停对应渠道自动付；核实支付回执 |
| 外部创单UNKNOWN出现 | P1 | 冻结该订单，向上游查单 |
| webhook验签失败激增 | P1 | 安全排查/封禁非法来源 |
| 订单进件延迟超过SLA | P2 | 检查MQ积压/API限流 |
| 发货回填失败积压 | P2 | 检查凭据和平台规则 |
| 数据库备份失败 | P1 | 立即补做备份 |
| 用户越权异常 | P1 | 临时限制受影响账户 |

阈值需随商家规模和真实平台API额度按压测调整。

## 备份与恢复
- 数据库每日全量+WAL/PITR，恢复目标以RPO≤15分钟、RTO≤4小时作为设计指标，生产演练后确定承诺值。
- 每季度进行恢复演练，记录耗时和完整性核验；确保备份数据加密、最小访问。
- MQ投递至少一次，重启后使用outbox重新恢复未投递事件。
- 自动付款渠道故障时先关停新扣款，再核实在途支付，避免重复尝试。

## 应急预案
- 渠道停机：转人工付款/暂停新采购、保留售后与查询。
- 金额异常：全局紧急停付，冻结在途不确定订单，通知商家与官方平台，人工对账。
- 凭据泄露：吊销/轮换、审计事件、通知受影响商家并按法定义务处理。
- 订单漏同步：采用独立官方增量对账作业，以平台权威状态回补。
