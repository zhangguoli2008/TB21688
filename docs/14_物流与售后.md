# 14 物流履约、包裹映射与售后处理

## 履约关联
销售主单可能有多个子项，单个子项可能因数量/发货仓不同拆成多个采购意图，采购单可产生多个Shipment。设计 `shipment_syncs` 关联上游包裹和下游销售子项/发货单，不能简单地一个订单只设一个tracking_no。

## 物流流程
1. 获取供应商物流事件和包裹信息；记录来源、时间和原平台状态。
2. 检查包裹是否覆盖某些销售子项数量，处理合单/拆单规则。
3. 根据下游平台获批的物流接口能力，提交发货信息。
4. 不以HTTP 200作为唯一成功条件，保存业务回执/平台返回的运单信息。
5. 回填失败进入补偿队列，显示具体原因和剩余发货时效。
6. 单号更改保存版本；平台不允许直接修改时提示人工渠道。

## 物流状态与告警
- `NOT_SHIPPED`, `PACKED`, `SHIPPED`, `DELIVERED`, `LOST`, `EXCEPTION`，均保留上游原始状态。
- 发货提醒：距平台时效<24h、<6h、已超时（阈值由平台承诺时间派生，避免写死）。
- 只有平台官方回填成功才更新 `downstreamAck=ACKED`。

## 售后策略
| 场景 | 本系统行为 |
|---|---|
| 下游未采购先取消 | 标记禁止采购，释放采购意图 |
| 上游已创单未付取消 | 根据上游接口申请关闭，确认状态后关闭 |
| 上游已支付且未发货取消 | 向上游发起取消/退款申请，不能承诺立即退款 |
| 上游已发货后退款 | 人工售后工作流及供应商退货协调 |
| 下游部分退款 | 更新对应销售子项应履约数量，避免其他子项错取消 |
| 下游售后仲裁 | 显示截止日期、证据清单、平台状态和处理人 |

## 退货地址
退货仓库与供应商退货地址分开；仅保存获得允许的必要商家/供应商业务地址，不混入消费者收货PII。退货地址变化须有审核与追踪。

## 关键测试
- 1下游单3子项跨2供应商，2个包裹回填正确。
- 上游运单号修改两次，只有最后获批版本正确。
- 订单刚取消同时付款Worker在途：支付前复核和售后补偿必须一致。
- 物流回填接口 5xx 重试不产生重复包裹记录。
