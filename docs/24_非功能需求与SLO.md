# 24 非功能性需求（NFR）、容量指标与服务目标

下列是**设计目标**，不是现有系统已测试的达成结果。生产SLO必须在试点与压测后修订。

| ID | 领域 | 初始目标 | 验证 |
|---|---|---|---|
| NFR-001 | 可用性 | 商家查询后台月可用性目标99.9%（平台外部故障另标注） | 生产监控/合约范围明确 |
| NFR-002 | 页面体验 | 常规列表API P95<500ms（不包含外部实时渠道调用） | 预期负载下压测 |
| NFR-003 | 异步订单 | 消息到本地队列P95<30s（不包含第三方推送延迟） | Mock场景监控 |
| NFR-004 | 扩容 | API/Worker无状态可独立横向扩展 | 多副本并发测试 |
| NFR-005 | 安全 | 无严重/高危未修复漏洞上线 | SAST/DAST/渗透测试 |
| NFR-006 | 隔离 | 跨租户API访问不泄漏数据 | 100%敏感API的反例测试 |
| NFR-007 | 支付正确性 | 支付UNKNOWN零盲目重试、零主动双扣 | 故障注入与对账 |
| NFR-008 | 数据正确性 | 销售与采购订单、支付、售后可独立对账 | 每日对账 + 人工抽查 |
| NFR-009 | 可追溯 | 外部副作用调用均关联trace/request/attemptId | 日志与平台回执关联 |
| NFR-010 | 容灾 | RPO≤15分钟、RTO≤4小时作为初始目标 | 恢复演练 |
| NFR-011 | 配置 | 无需重新部署可按通道/租户紧急停自动付款 | 演练记录 |
| NFR-012 | 兼容性 | 近两主版本Chrome/Edge，1024及以上桌面布局 | 浏览器E2E |
| NFR-013 | 开发效率 | 新渠道只新增Adapter +能力声明 +测试 | 编写示例Fake Adapter |
| NFR-014 | 隐私 | 业务库、HTTP日志不持久化消费者明文收件地址 | 数据扫描和日志检测 |

## 压测模型（先建负载模型再选择云实例）
- 模型A：10个租户各2店铺，每店每日100笔订单，5%售后、10%需要人工匹配。
- 模型B：30租户各10店，每店每日300笔订单，事件高峰集中于2小时；观察消息队列延迟和数据库锁。
- 模型C：付款回调瞬时重复20次、创建订单并发100次、外部API超时30%，验证幂等与补偿。
- Mock Provider必须可配置延迟、超时、429/5xx和重复回调，模拟真正的故障场景。

## 变更策略
API破坏性变更必须升版本；重要事件schema升级要求向后兼容；数据库迁移使用滚动发布兼容期。涉及支付策略或租户权限的行为变更必须人工review。
