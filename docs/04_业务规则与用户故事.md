# 04 业务规则与用户故事

## 术语
- SalesOrder：顾客在淘宝/抖音产生的销售单。
- FulfillmentGroup：需共同履约的销售子单集合；可能一单拆成多个上游采购。
- PurchaseIntent：经过SKU匹配的待采购意图；可关联最多一笔当前有效的上游采购单。
- PurchaseOrder：供应商侧创建的采购订单。
- PaymentAttempt：发起一次支付的执行记录，`UNKNOWN` 不允许再发起新尝试。
- PaymentMandate：商家与获批支付通道的自动付款签约状态引用。
- Shipment：供应商产生的包裹/运单；可能多包裹。
- Mapping：某个销售SKU到供应商SKU的已确认映射关系。

## 核心规则
- BR-001：`source_platform + shop_id + source_order_id` 全局唯一，平台重试消息只更新，不生成新订单。
- BR-002：同一个已确认 sales order item 的剩余可采购数量不得超过待履约数量；取消/退款影响可采购数量。
- BR-003：自动采购只允许 `CONFIRMED + ACTIVE` 的 SKU 映射；AI相似度无论多高都不等于 CONFIRMED。
- BR-004：采购前重新查询销售状态、供应商最新价格、SKU库存、履约通道、限额；读取过期的报价须重查。
- BR-005：业务利润的默认公式 `预计毛利=销售分摊实收-上游商品成本-采购运费-预估平台费-预估售后损耗`。显示“估算”，实际利润需支付回执、退款/补偿等确认。
- BR-006：金额按 CNY 分存储；所有折扣/退款分摊保留可审计的分配依据，四舍五入尾差落在最后一项。
- BR-007：`MANUAL` 不自动扣款；`AUTO` 必须有有效支付签约及通道能力；`RULE_BASED` 满足阈值才自动付。
- BR-008：支付 `UNKNOWN` 不可执行二次自动支付，亦不可立即开放人工二次付款。
- BR-009：订单价格/数量/供应商在支付确认前改变时，订单冻结并重新审批，不允许静默继续。
- BR-010：上游发货不等于下游已回填。回填成功需官方接口权威回执，失败应单独重试。
- BR-011：已付款采购单不能简单“取消成功”；须依据供应商实际取消/退款结果落状态。
- BR-012：平台OAuth失效/解除授权时停止新同步及相关写操作，保留依法允许留存的最小业务记录。
- BR-013：业务锁/幂等是双保险。网络超时的上游下单也必须先按外部订单关联查状态，不能盲重试。
- BR-014：单租户停机/冻结仅中止该租户新任务；现存发货/售后需要安全可见的收尾路径。
- BR-015：拼多多普通买家创单和扣款能力默认为 `UNAVAILABLE`，审批确认前不可对外宣传支持。
- BR-016：关键操作记录操作者ID、时间、业务对象、动作、变更摘要，不存隐私明文。
- BR-017：发货截止时间以原平台最新承诺时效为准，平台规则变化时动态更新。
- BR-018：收货地址必须按下游平台许可的密文/面单能力流转；不能把密文自行解出并作为另一平台普通买家地址。

## 规则优先级
系统安全和合规硬门禁 > 平台通道能力 > 租户紧急暂停 > 支付授权状态 > 店铺规则 > SKU专属规则 > 租户默认规则。遇规则冲突时取**更严格**的金额/风险约束，不以用户设置覆盖硬门禁。

## 核心用户故事
- US-01（店主）：作为新商家，我希望在一个页面看到绑定了哪些店铺、各自授权是否过期，减少遗漏。
- US-02（采购员）：作为采购员，我希望找到已购商品的候选货源，并准确核对型号/数量以避免错发。
- US-03（店主）：作为店主，我希望在符合利润和限额时自动采购，不符合就进入审批队列。
- US-04（财务）：作为财务，我希望付款显示平台核实状态，并对每笔付款追踪上游凭证与退款。
- US-05（客服）：作为客服，我希望看到客户退款后上游能否取消和物流状态，而不是默认已经退款。
- US-06（管理员）：作为管理员，我希望可以停用出错的采购通道而不影响其他用户日常查询。

## 边界案例
- 两个平台都使用相同订单编号：凭渠道 + 店铺ID去重，互不影响。
- 同店订单拆成多种颜色：逐销售子项匹配，SKU与数量不能合并错。
- 客户购买三件供应商只剩两件：不自动变更数量，转人工。
- 采购报价¥35.00，创建采购时变¥42.00：暂停付款/重新审批。
- AUTO付费请求已发出但HTTP 504：UNKNOWN，平台查单，不再次扣款。
- 原销售单在采购前取消：停止采购；采购后取消：提交上游取消/售后任务。
- 供货商发两个包裹：两个 Shipment，遵循下游分包规则回填。
- 成本不完整：不展示“准确净利润”。
