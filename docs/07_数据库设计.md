# 07 数据库逻辑设计与约束

参考的可执行DDL草案见 `database/schema.sql`；Codex必须把它拆成Flyway版本迁移，而非直接上线执行。

## 多租户总体模型
`Tenant (1) -> Store(N) -> SalesOrder(N) -> SalesOrderItem(N)`
`Tenant (1) -> SupplierAccount(N) -> SupplierOffer(N)`
`SalesOrderItem (N) -> SkuMapping(0..N) -> SupplierSku`
`SalesOrderItem -> PurchaseIntent(N) -> PurchaseOrder(0..1有效) -> PaymentAttempt(N)`
`PurchaseOrder -> Shipment(N) -> ShipmentSync(N)`
`SalesOrder -> AftersaleCase(N)`
`Tenant -> PaymentPolicy(1..N), PaymentMandate(N), AuditLog(N), Subscription(1)`。

| payment_mandates | tenant_id, supplier_account_id, provider, reference, status | 不保存支付密码 |
| sales_orders | store_id, external_order_id, source_status, paid_amount_fen | UNIQUE(tenant_id,store_id,external_order_id) |

## 设计约束
1. `tenant_id`不接受客户端直接指定，取登录上下文绑定租户；唯一索引把tenant_id纳入业务唯一性。
2. 外键尽量包含tenant_id，以防跨租户错误关联；适当采用复合唯一约束供外键引用。
3. 用 `BIGINT amount_fen`，不使用浮点数存钱；比例用 `NUMERIC(8,4)` 或整数bps。
4. 业务事件状态与平台原始状态分列；不要覆盖不同时序。
5. 所有采购、支付和退款状态行有 `version` 乐观锁；关键更新用 CAS。
6. 列表常用索引：`(tenant_id,store_id,created_at DESC)`, `(tenant_id,state,updated_at)` 等；生产根据EXPLAIN调整。
7. `audit_logs`存变更摘要/哈希，生产可配置WORM存储保留；不得写入敏感密钥/真实地址。
8. 不持久化明文消费者姓名、电话和详细地址；合法必须临时处理时应通过获准的受控环境，不落普通业务库。
9. 订单删除/过期遵从数据保留与法定留存要求，采用精细化清理，不影响财务审计凭证。

## 关键唯一性
- `inbox_events(provider, integration_id, event_id)` UNIQUE。
- `purchase_intents(tenant_id, source_item_id, fulfillment_slice_no)` UNIQUE。
- `purchase_orders(tenant_id, purchase_intent_id)` UNIQUE（若需要重建明确引入版本而不是多建）。
- `payment_attempts(tenant_id, purchase_order_id, attempt_no)` UNIQUE。
- `outbox_events(event_id)` UNIQUE。
- 外部上游订单ID可能只在同一供应商账号下唯一，UNIQUE须包含 `supplier_account_id`。

## 生命周期和清理
- OAuth授权撤销后删除或吊销 token secret，保留必要审计状态。
- 订单记录和支付审计按商家协议、平台政策、法规制定分类保留，禁止在未确认期限前写死统一清理天数。
- 合成测试数据与真实数据严格隔离；真实数据禁止复制到测试环境。
