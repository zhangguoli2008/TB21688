# 18 Codex 开发里程碑与可验收任务池

开发原则：每阶段都留下可运行仓库、CI测试和可演示界面。预计时间仅用于排期，不代表异步承诺。无真实平台权限不阻断Mock开发。

## M0 项目基础（推荐首先交给Codex）
- SP-001 monorepo Maven/Gradle + Vue3 Vite + Docker Compose + GitHub Actions。
- SP-002 Swagger/OpenAPI契约 + 全局错误结构、请求校验、requestId。
- SP-003 Flyway初始表、开发用演示数据初始化工具。
- SP-004 Security认证、用户会话、租户上下文、RBAC拦截器。
- SP-005 Mock平台适配器、基于配置切换能力与禁用真实访问。
- DoD: `docker compose up` 启动API、Web、PostgreSQL、Redis、RabbitMQ；登录到空仪表盘；测试可运行。

## M1 店铺及订单
- SP-101 店铺CRUD、Mock授权状态（有效/过期/撤销）。
- SP-102 合成订单事件Webhook/入库去重、官方订单详情查询抽象。
- SP-103 销售订单/子项列表详情、筛选、时间轴。
- SP-104 越权与事件乱序处理单元/集成测试。
- DoD: 两个租户的同名外部订单不互相可见，重复事件不重复入库。

## M2 商品与采购
- SP-201 SKU映射管理、版本与审计。
- SP-202 Mock供应商商品报价/运费/库存/密文能力模拟。
- SP-203 采购规则引擎（利润、限额、发货区域和供应商优先级）。
- SP-204 采购意图状态机、唯一性、外部采购单模拟与UNKNOWN恢复。
- DoD: 映射后订单自动产生有效采购意图；错误SKU与异常报价被阻断。

## M3 双模式付款
- SP-301 支付策略（MANUAL/AUTO/RULE_BASED）、签约状态模拟。
- SP-302 商家官方收银台Mock入口（仅模拟URL，实际生产按官方规定）。
- SP-303 PaymentAttempt状态机、金额风控、日额度预占。
- SP-304 UNKNOWN冻结、权威查单模拟、对账任务。
- SP-305 UI支付中心、待付款列表、授权状态提示。
- DoD: AUTO可在Mock签约下自动成功，MANUAL经Mock付款成功，UNKNOWN不会二次付。

## M4 履约与售后
- SP-401 多包裹Shipment及下游回填状态机。
- SP-402 售后工单、取消/退款协调。
- SP-403 利润报表、经营大屏、通知和审计展示。
- DoD: 采购已付→模拟供应商发货→正确包裹回填→售后流程可见。

## M5 商用品质
- SP-501 多用户店铺范围权限、MFA和高危操作再认证。
- SP-502 用量、套餐、配额及平台管理员后台。
- SP-503 对账、死信中心、监控、备份和灰度开关。
- SP-504 压力、安全、越权、隐私泄露扫描及修复。
- DoD: T-001~T-025关键场景全通过，生产默认真实通道关闭。

## M6 真实平台准入与集成（条件触发）
- SP-601 抖店合规审批 + OAuth + 订单/售后/物流SDK。
- SP-602 淘宝应用授权 + 订单/物流 + 密文分销能力。
- SP-603 1688实际获批采购/查单/物流/支付状态能力。
- SP-604 1688官方付款页，支付签约与AUTO（需批准）。
- SP-605 拼多多如存在合规买家采购/支付渠道，再独立申请、实施和测试。
- DoD: 每条生产接口有授权证明、合同文档、sandbox/真实小流量验证、可停用开关、日志/对账及回滚预案。

## 工作量/排期假设
- M0–M3：可以交给Codex按模块迭代实现，建议先做可演示业务路径，严禁盲目一口气实现全部。
- M4–M5：需较完整测试、安全、部署和运营投入。
- M6取决于第三方审批时间，不可将“未获批”变成“已上线”。
