# 06 系统技术架构（可编码版）

## 总体原则
模块化单体优先，领域边界清晰，异步任务独立Worker进程；平台接口统一防腐层，生产功能需审批；前后端API分离。避免早期拆成十几个微服务造成分布式事务与维护压力。

## 逻辑分层
```
浏览器(Vue3/Element Plus)
  -> HTTPS / WAF / reverse proxy
  -> API Spring Boot
     - identity (认证、租户、RBAC)
     - stores (店铺与授权)
     - sales (销售订单)
     - catalog (商品、SKU映射)
     - sourcing (候选货源、报价、规则)
     - purchase (采购意图与上游订单)
     - payments (支付签约、策略、支付尝试、对账)
     - logistics (包裹、回填)
     - aftersales (退款/售后)
     - reporting (统计投影)
     - billing (订阅、套餐、配额)
     - admin (平台配置、运维)
     - audit/notifications (审计、通知)
  -> PostgreSQL / Redis / RabbitMQ / object storage
  -> worker-process(es)
  -> ProviderAdapters [Mock, Douyin, Taobao, 1688, PDD-vetted]
  -> 官方渠道API / 允许的密文履约环境
```

## 模块调用边界
- 销售模块只发布 `SalesOrderPaid` 领域事件，不直接调用支付平台。
- 采购模块从映射和报价获得快照后提交 `PurchaseIntentApproved`，由Worker异步触发上游。
- 支付模块根据 `PaymentCapability` 和商家策略决定执行 `AutoDebit` 还是 `ManualCheckout`。
- 物流模块收到 `SupplierShipmentObserved` 后独立触发下游回填。
- 报表服务读取订阅的领域事件投影；关键资金指标可以与源表每日对账。

## Platform Adapter 接口
```java
interface SalesPlatformAdapter {
  CapabilitySet capabilities();
  OrderSnapshot fetchOrder(StoreContext store, String externalOrderId);
  List<OrderSnapshot> reconcileOrders(StoreContext store, Instant since);
  ShipmentAck reportShipment(StoreContext store, ShipmentSubmission shipment);
}
interface SupplierAdapter {
  SupplierCapabilities capabilities(SupplierAccount account);
  Quote quote(QuoteRequest request);
  PurchaseCreateResult createOrder(PurchaseRequest request, String idempotencyKey);
  PurchaseSnapshot getOrder(String externalId);
  CheckoutEntry officialCheckout(String externalId);
  PaymentResult executeAuthorizedPayment(String externalId, String mandateRef, String attemptRef);
  PaymentResult queryPayment(String externalId);
  List<ShipmentSnapshot> queryShipments(String externalId);

```
注：以上全是**内部接口**；实际1688/拼多多权限决定是否能够实现某个方法。能力缺失返回明确错误并禁用UI。

## 资源与部署建议
- 开发：1个API实例、1个Worker实例、PostgreSQL、Redis、RabbitMQ、MailHog/Mock、Vite。
- 小规模生产：API至少2副本、Worker可横向扩展；托管数据库主备/备份；Redis和MQ高可用视需求分阶段；对象存储、WAF、日志服务。
- 初期不强制Kubernetes；生产采用容器编排或云托管容器服务，提供健康检查与滚动发布。
- 目标RPO/RTO：建议初期 RPO<=15分钟、RTO<=4小时，属于设计目标，需演练验证。
- 容量阈值及真实服务器规格必须在压测后确认，不从订单量直接猜机器数量。

## 一致性策略
- 基于本地事务 + outbox + async worker 的最终一致性。
- 支付、采购创单采用业务幂等键与权威状态重查；数据库唯一约束不可省。
- MQ以至少一次投递为前提设计，不宣称exactly-once delivery。
- Redis锁可作为效率辅助，但正确性以数据库约束/CAS和外部状态核验为准。

## 可观测性
- 日志结构化字段：timestamp, traceId, requestId, tenantRefHash, storeRefHash, entityId, action, channel, outcome, code, durationMs。
- 指标：订单进件延迟P95、供应商API失败率、任务队列积压、采购冻结数量、支付UNKNOWN数量、待人工数量、发货回填时延、对账差异。
- 链路追踪：HTTP API→事件Outbox→Worker→ProviderAdapter，敏感请求体禁止入traces。
