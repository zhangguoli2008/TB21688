# 10 双支付模式、自动付款签约与风险控制

## 付款前提
商家自有采购账号 + 有效采购业务授权 + **独立**支付协议/官方允许的付款入口。SaaS不直接托管采购款；不接收支付密码、商家验证码和支付卡敏感信息。

## 支付模式
- `MANUAL`：创建上游采购单后在SaaS等待付款；显示官方认可的收银台入口或采购单官方页面。商家完成支付后由权威状态查验，禁止点击“已支付”直接确认。
- `AUTO`：满足实际通道可用、签约有效、商家限额、风控准入、SKU确认且不涉未解决售后时自动扣款；条件不满足，按明确规则转待人工/审核。
- `RULE_BASED`：将金额、利润、SKU、供应商信任分、区域、店铺、日累计等作为条件；低风险自动，其他人工。

## 支付审批
- 修改支付策略、提升上限、启停免密，需要 `paymentPolicy.manage`，可配置MFA + 双人审批。
- 合作通道签约由商家在官方页面完成；本系统只读取状态/引用。
- 每笔采购必须与授权租户、采购账号和支付签约主体关联，不能跨商家共用支付授权。

## 自动扣款门禁决策表
| 条件 | 决策 |
|---|---|
| 未匹配/映射待确认 | MANUAL_REVIEW，不能自动采购 |
| 下游订单取消或退款中 | BLOCKED，若已上游付款走售后补偿 |
| 供应商不支持所需密文面单 | BLOCKED或合规换供 |
| 供应商价格/库存过期 | REFRESH_QUOTE |
| 不满足预计利润/运费/金额阈值 | MANUAL_REVIEW |
| 支付模式MANUAL | WAIT_MERCHANT_PAYMENT |
| AUTO + 未签约/失效/超额 | WAIT_MERCHANT_PAYMENT（仅未在支付中时） |
| AUTO + 通道不支持 | WAIT_MERCHANT_PAYMENT或DISABLED |
| AUTO + 已签约、规则通过 | PAYING，Worker调用获批支付能力 |
| 支付请求超时或结果未知 | UNKNOWN，冻结、对账，不可再支付 |

## 安全预算与限额
- 平台上限与商家上限同时生效，取较小值。金额上限字段用分整数存储。
- 已发起/在途支付都预占当日预算，确认失败才释放，防止并发超扣。
- 租户单笔限额、日额度、每店额度、供应商黑名单、新供应商首次采购人工审核。
- 大额/策略修改/新设备登录增加强认证与操作审计。
- 账户授权被撤销时立即禁用发起新支付；在途尝试继续只读对账，不可二次扣款。
- 余额/授信不足返回明确业务原因，不允许反复发起付款。

## 采购付款一致性
1. `PurchaseOrder` 创建成功仍为待付款，不得提前发物流。
2. 每次调用外部支付前持久化唯一 `PaymentAttempt` 和幂等键。
3. 本地状态 `PAYING` 与支付请求异步隔离。
4. 收到返回或回调后执行权威查单/核验：上游账号、订单ID、金额、币种、状态一致才标记PAID。
5. `UNKNOWN`冻结：只能通过官方查单得出明确结果或人工解决，不得自动再次扣款，也不得自动开放人工重付。
6. 日终对账：对比本地采购单、外部采购流水、支付状态和退款记录，形成可追溯差异单。
7. 全局紧急停付开关独立于自动采购开关，可在控制台强制停新自动支付。

## 支付策略示例（仅演示，非真实默认限额）
```
mode: RULE_BASED
maxSinglePayFen: 5000
maxDailyPayFen: 200000
minimumEstimatedProfitFen: 1500
requireConfirmedMapping: true
requireCiphertextFulfillment: true
newSupplierFirstOrder: MANUAL_REVIEW
onNoMandate: WAIT_MERCHANT_PAYMENT
onPaymentUnknown: FREEZE_AND_RECONCILE
```

## 预先定义的支付对账作业
- 每5分钟检查逾时PAYING/UNKNOWN（频率为产品默认假设，可按平台限流调整）。
- 先按上游采购ID查询，若支持再查询支付流水；查询仍无法确认则转人工而非再次提交。
- 定期报告：待付款数量、冻结金额、未知笔数、对账不平金额。

## 禁止的实现方式
- 用浏览器自动输入支付宝/微信支付密码；保存Cookie维持付款登录；绕过平台安全验证。
- 在支付结果UNKNOWN后创建第二个付款任务。
- 用未经平台批准的第三方代付实现跨商家集中采购。
